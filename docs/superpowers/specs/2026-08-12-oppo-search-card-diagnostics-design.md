# OPPO 搜索商品卡只读诊断设计

## 背景与已确认事实

2026-08-12 的 OPPO 官网实机运行中，A5m 与 A6t 都成功提交搜索并显示结果，但三次尝试均在进入详情页前以 `LAYOUT_CHANGED` 结束。任务数据库没有形成详情页观察检查点，失败边界因此位于“搜索结果稳定后、进入详情页前”。

当前生产代码已经满足两条业务规则：

- 商品卡显示缺货仍允许进入详情页；
- 任务名称包含 `5G`、商品卡未显示 `5G` 时仍允许按同一基础机型匹配。

本轮不再放宽这两条规则，而是取得真实搜索卡结构证据。

## 目标

当 OPPO 搜索结果无法选出并进入合法详情页时，生成一份完全本地的只读诊断文件。文件应能回答每张可见商品卡：

1. 链接元素自身的 `aria-label`、`title` 与可见文字是什么；
2. 链接内部候选标题元素的文字是什么；
3. 原始 `href` 与规范化后的链接是什么；
4. 程序判定的基础机型是否精确匹配；
5. 链接是否属于允许的 OPPO 数字商品详情地址；
6. 该卡被接受或拒绝的明确原因。

## 范围与隔离

- 只修改 OPPO 官方适配器及其契约测试。
- 只在搜索结果阶段发生 `LAYOUT_CHANGED` 前写诊断。
- 不修改搜索词、等待时间、商品卡顺序、点击方式、详情页配置选择、价格、截图、Excel 或执行报告汇总规则。
- 不修改荣耀、小米、京东、天猫及其他品牌官网。
- 不读取或保存 Cookie、Local Storage、账号、地址、手机号、浏览历史或页面外数据。

## 数据格式与保存位置

使用 UTF-8 JSON，保存到应用现有本地证据目录下的 OPPO 诊断子目录。文件名包含任务 ID 与尝试时间，避免覆盖前一次证据。顶层字段包括：

- `task_id`、`run_id`、`model_name`；
- `page_url`、`search_keyword`；
- `search_scope_found`、`result_region_found`、`explicit_empty_result`；
- `cards`：按页面可见顺序排列的逐卡记录；
- `failure_stage` 与稳定的内部原因码。

诊断文字应做长度上限，避免保存整页文本或无关大段营销内容。

## 触发与错误处理

- 正常找到合法精确机型卡并进入详情页时不生成诊断文件。
- 搜索结果稳定后仍没有可进入的合法精确机型卡，或搜索结果在有可见卡时无法稳定，生成一次诊断再保留原有技术失败语义。
- 写诊断本身失败时不得覆盖原始错误，也不得使浏览器任务产生新的重试或状态变化。
- 执行报告继续显示 `LAYOUT_CHANGED`；更具体的诊断路径通过现有任务技术错误证据链保存，后续再决定是否需要把摘要写进报告。

## 测试与验收

必须先写失败契约，再写生产代码：

1. 正常精确卡可进入时不生成诊断；
2. 链接自身是泛化文字、内部标题是正确机型时，诊断同时记录两者；
3. 缺货与缺少 `5G` 只作为原始文字记录，不得成为拒绝原因；
4. 非法链接与近似机型分别记录不同拒绝原因；
5. 诊断写入失败不改变原始 `LAYOUT_CHANGED`；
6. OPPO、荣耀、小米、品牌隔离和报告/Excel代表性回归保持通过。

完成诊断版后只构建新的 Mac 测试包，不覆盖 `.64`。用户再运行一次后，根据真实 JSON 证据确定唯一的生产修复。
