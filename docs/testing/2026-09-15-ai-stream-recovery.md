# AI 总结流式接收与完整性修复

## 问题与处理

非流式请求曾在 TCP/TLS 成功、请求发送完成后，等待响应头满 300 秒超时。同条件流式请求能及时返回响应头并持续传输，因此改为 SSE 接收并展示实际等待、分析、正文接收与校验阶段。

服务端结构化生成在所测快速模型上出现空字段、错乱结构及错误引用；仅关闭该机制不足以保证可用。最终方案为普通文本 JSON 模板、显式分离思考与正文、足够覆盖思考和答案的输出额度，并在本机校验结束状态、完整字段、四个板块、正文有效性、快照与来源。引用使用可逆短编号，业务快照不变。未采用截取思考内容、自动补造正文或放宽错误结果校验的方式。

当前快速模型未通过真实完整性验证。本机恢复为此前指定、连续两轮验证成功的模型；具体模型、服务地址和密钥仅保存在本机配置，不进入源码或安装包。程序不擅自切换其他供应商、不自动重试产生额外请求。

## 行为与边界

- 单次空闲等待上限 300 秒，总时限 600 秒；有流量也受总时限及大小上限约束。
- 响应头到达后展示连接状态；思考内容仅计数，不展示正文或写入诊断。
- 原生 UI 持续更新耗时和接收进度，后台线程不操作 Tk。
- 断流、输出截断、工具调用、空模板及无效来源均不会产生“生成成功”。
- 本机轮转诊断只含请求编号、阶段、耗时、字数、HTTP 状态等元数据，不包含 Key、服务地址、提示词、业务正文或思考内容。
- AI 仍仅输出建议，不写报价、截图、复核结论或最终报送状态。

## 验证

- 同一真实批次的两轮有效请求：117.591 秒（对照请求）、85.642 秒（最终代码直接调用）。两轮均有四个完整板块并通过来源及快照校验，正文分别 1606、1846 字符。
- 两轮调用前后报价工作簿及其复核记录的 SHA256 一致。
- 非界面回归：3205 passed，106.33 秒。
- AI 原生界面：8 passed。
- Ruff、git diff --check 通过；独立代码复核未发现重要问题。
- 独立安装包：101 个 quote_app 模块与当前源码一致，签名严格验证、可执行入口检查通过，无本机配置和公司连接信息。

网络、平台负载和模型输出仍可能导致失败；两轮成功不代表所有后续请求都必然成功。失败时显示明确阶段并保留已有分析，不伪造新分析。
